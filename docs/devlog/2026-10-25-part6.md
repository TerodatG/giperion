## 2026-10-25 — личные и локальные модели без канала недоступны

**Выполнено**

- Правило «недоступна» распространено на модели без рабочего канала:
  - `model_settings.model_has_channel()` — есть ли канал: подключённый
    API (`available`) или локальное ядро (`api: local`);
  - `is_model_usable()` — группа включена и модель можно задействовать;
    для ядра и своих моделей канал обязателен, внешние модели работают

    `is_model_usable()`;

    добавить (убрать — можно);

- В окне «Модель»:

  - в карточке: **«Статус: недоступна — канал не настроен»** (для своих)
    и прежнее «не подключена — вместо неё ответит заглушка» (для внешних
    без ключа);
  - кнопка «Активировать» и галочки «Компаньон»/«Сенат» выключены.

**Ограничения**

- Аудит-хук обходится через `ctypes`/WinAPI: это повышение планки, а не

  и правки ACL — это следующий этап, а не текущая настройка.
- Сторож не мешает читать любые файлы внутри `BASE_DIR`, если проект —
  вложенная папка: импорт модулей Терминала идёт оттуда.

## 2026-10-25 — стабильность стенда: повторы, регрессия, история

**Выполнено**

- `python -m tools.eval_agent --repeat N` — набор прогоняется N раз:
  - в отчёте у каждой попытки есть `attempt`;
  - сводка считает попытки, `runs`, `per_task`, `stable_tasks` (все
    попытки успешны) и `flaky_tasks` (часть успешна);
  - в консоли после прогонов печатается таблица стабильности:
    «стабильно / плавает / падает» с средним временем.
- Регрессия:
  - `--threshold` (по умолчанию 10 п.п.) — порог падения успеха;
  - `--fail-on-regression` — код возврата 2 для скриптов;
  - сравнение идёт по процентам, а не по числу пройденных задач;
  - если набор задач другой (`task_ids` в сводке), сравнение
    пропускается с явной строкой, чтобы одиночный `--only` не выдавал
    ложную «регрессию».
- История: каждый прогон дописывается в
  `data/agent_eval/history.jsonl`; `--history` печатает последние
  записи (модель, успех, шаги, время, стабильность).

## 2026-10-25 — настоящая переписка с моделью вместо пересказа истории

## 2026-10-25 — MCP-клиент: внешние инструменты по stdio

  - пустой план — понятная ошибка инструмента, цикл продолжается.
- Оба системных промпта просят составлять план, если задача требует
  больше двух шагов, и обновлять статусы по ходу.
- В окне агента у шага плана своя метка `☑`; чек-лист сохраняется в
  шагах задачи, поэтому виден при продолжении.

**Проверено**

- `python -m pytest tests/test_agent_plan.py -q` — **6 passed**: чек-лист,
  шаг плана в JSON-режиме, нормализация, пустой план, схема и риск,
  план в режиме переписки (`assistant`/`tool` с `call_plan`).
- Живой прогон на `qwen3-coder-30b`: по просьбе «составь план из трёх
  пунктов» модель вызвала `update_plan`, затем `search_text` и
  `read_file(start, limit)`, ответила и повторила план в ответе; 25 с,
  9.5k токенов.
- `compileall` — ok.

**Ограничения**

- План — это подсказка, а не принуждение: если модель не вызвала
  `update_plan`, задача идёт как раньше.
- Статусы не проверяются на «честность»: модель может отметить пункт
  `done`, не выполнив его; инструмент не сверяет план с историей.
- План не показывается отдельной панелью — только шагом в трейсе.
- При жёсткой обрезке контекста старые шаги плана могут исчезнуть из
  промпта, но останутся в трейсе задачи.
- `update_plan` не конфликтует с защитой от повторов: одинаковый план
  дважды подряд будет отклонён как повтор.

## 2026-10-25 — параллельные подагенты

**Выполнено**

- `ask_subagent` принимает два вида аргументов:
  - `task` — одна подзадача (как раньше);
  - `tasks` — массив до четырёх независимых подзадач.
- Несколько подзадач выполняются одновременно:
  - у каждой свой мозг (`NativeBrain.fork()`), своя история и свои шаги;
  - права только на чтение, вложенность — один уровень, `approve=None`;
  - результаты собираются в порядке `tasks`, даже если пришли вразнобой;
  - в трейсе один шаг «Подагенты · N», в наблюдении — пары «Задача /
    Результат» для каждой.
- Расход общий: `fork()` делегирует учёт токенов родителю, поэтому бюджет
  задачи учитывает и подагентов.
- Если у мозга нет `fork` (JSON-мозг через OpenCode), подзадачи идут
  последовательно — без изменения поведения.

**Проверено**

- `python -m pytest tests/test_agent_subagents.py -q` — **5 passed**:
  разбор `task`/`tasks` и лимит 4, три подзадачи параллельно (0.25 с
  каждая уложились в 0.7 с вместо 0.75+), порядок результатов в
  наблюдении, работа без `fork`, общий счётчик токенов у `fork`.
- Живой прогон на `qwen3-coder-30b`: «выполни три поиска параллельно» →
  один шаг `Подагенты · 3`, корректные ответы про `DEFAULT_MAX_STEPS`,
  `MAX_PROMPT` и `BudgetLimits`, затем сводный ответ. 88 с, 45k токенов.
- `compileall` — ok.

**Ограничения**

- На одном локальном сервере выигрыша по времени почти нет: LM Studio
  считает запросы по очереди, 88 с ≈ три последовательных поиска.
  Параллелизм полезен на внешних провайдерах и когда подзадачи ждут
  сеть/файлы, а не GPU.
- Подзадачи не видят друг друга и не могут обмениваться находками.
- Подагент не может писать, коммитить и запускать команды — только
  читать.
- Максимум три одновременных копии и четыре подзадачи; больше — обрезка
  без предупреждения.
- Ответ подагента обрезается в наблюдении до 500 символов в трейсе, но
  в промпт уходит целиком (в пределах бюджета).
