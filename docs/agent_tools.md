# Плагины инструментов агента

Плагины добавляют агенту «Терминала» собственный инструмент. Они
**выключены по умолчанию** и включаются вручную: окно агента →
«Провайдер…» → **«Разрешить плагины инструментов»**.

## Изоляция

- При загрузке читается только **JSON-манифест** — код плагина не
  исполняется.
- Каждый вызов плагина запускается в **отдельном процессе** Python.
- Таймаут — 30 секунд; зависший процесс убивается.
- Окружение очищается: плагин получает только системный минимум (PATH,
  TEMP, SYSTEMROOT), `PYTHONPATH` проекта и `PYTHONIOENCODING`. Ключи,
  токены, пароли и прокси-переменные не передаются.
- Рабочая папка процесса — **папка проекта**, а не папка Терминала.
- Лимиты Windows Job Object: **512 МБ памяти** и **30 секунд CPU** на
  процесс; при превышении процесс завершается, Терминал получает
  понятную ошибку.
- Внутри плагина стоит сторож (`sys.addaudithook`): чтение и запись за
  пределами папки проекта, сокеты и запуск программ блокируются
  `PermissionError`. Временная папка плагина — `.agent_plugin_tmp`
  внутри проекта.
- Падение или исключение плагина не роняет Терминал: агент получает
  ошибку инструмента.
- Вывод плагина подавляется, наружу идёт только JSON-результат.

Сторож — это защита от случайного и честного кода: он перехватывает
`open`, `os.*`, `socket.*` и `subprocess.Popen`, но не является границей
ОС. Код, который сознательно обходит аудит через `ctypes` и вызовы
WinAPI, теоретически может её пройти. Для настоящей границы нужен
AppContainer (см. ниже). Включайте только код, которому доверяете.

## AppContainer: состояние вопроса

Проверено на этой машине (Windows 11, build 26300). Песочница
**работает** и включается в окне «Провайдер…» → «Песочница:
AppContainer (Windows)».

Подготовка (один раз, ~93 МБ):

```powershell
python -m tools.setup_plugin_container --prepare
```

Что делает подготовка:

1. копирует Python в `data/plugin_python` (без `site-packages`);
2. создаёт профиль AppContainer `Giperion.Agent.Plugin` и получает SID;
3. выдаёт контейнеру чтение проекта (`terminal`, `shared`, `giperion`,
   `docs`, `tests`, `tools`, файлы корня) и запись только в его
   временную папку;
4. запускает `python -c "print('container-ok')"` внутри контейнера;
5. проверяет, что домашняя папка пользователя недоступна, и печатает
   «изоляция: заблокировано».

Что получается:

- проект **только читается** — запись в файлы проекта запрещена на
  уровне ACL;
- если плагин объявил `fs:write`, ему выдаётся **отдельная папка**
  `data/agent_plugin_out/<имя_плагина>` (путь в переменной окружения
  `AGENT_PLUGIN_OUT`), и писать можно только туда;
- домашняя папка, чужие диски и системные данные недоступны;
- **сеть запрещена ОС**: у контейнера нет возможности `internetClient`,
  поэтому DNS не резолвится (`getaddrinfo failed`), а соединения по
  IP отклоняются (`WinError 10013`);
- запись разрешена только во временную папку контейнера;
- поверх этого работает тот же `guard.py` (аудит-хук), то есть защита
  двухслойная.

Удалить песочницу и права:

```powershell
python -m tools.setup_plugin_container --remove
```

Ограничения режима:

- плагин с `fs:write` в контейнере получает запись только в
  `data/agent_plugin_out/<имя_плагина>`; файлы проекта остаются
  доступными только для чтения;
- нужна отдельная копия Python, потому что установка из
  `Program Files\WindowsApps` контейнеру недоступна (проверено:
  `STATUS_DLL_NOT_FOUND` / `0xC0000142`);
- при обновлении Python копию нужно пересоздать:
  `--prepare --force`;
- AppContainer есть только на Windows; на других ОС остаётся режим
  «Процесс + сторож».

## Разрешения

Манифест может объявить, что плагину нужно:

```json
"permissions": ["fs:read", "fs:write"]
```

- `fs:read` — чтение файлов проекта (по умолчанию);
- `fs:write` — запись (по умолчанию для `risk=write` и `risk=exec`);
- `exec` — запуск программ (только при `risk=exec`);
- `net` — сеть (только при `risk=exec`).

По умолчанию набор зависит от `risk`: `read` → `["fs:read"]`,
`write` → `["fs:read", "fs:write"]`, `exec` → плюс `exec`. Плагины с
`net` или `exec` **не загружаются**, пока в окне «Провайдер…» не включена
галочка «Разрешать плагинам сеть и запуск программ».

## Файлы

`data/agent_tools/` — на каждый плагин два файла:

```
data/agent_tools/my_tool.json   # манифест
data/agent_tools/my_tool.py     # код
```

Манифест:

```json
{
  "name": "my_tool",
  "description": "Короткое описание для модели.",
  "args": {"path": "что означает аргумент"},
  "required": ["path"],
  "risk": "read",
  "permissions": ["fs:read"],
  "module": "my_tool.py",
  "handler": "handler"
}
```

Модуль:

```python
from terminal.core.agent.protocol import ToolResult


def handler(root, args):
    path = args.get("path", "")
    return ToolResult(True, f"Плагин получил путь: {path}")
```

## Правила

- `name` — уникальное, `[a-z][a-z0-9_]{2,30}`, не совпадает со
  встроенными инструментами.
- `args` — словарь «имя → описание», все аргументы строки.
- `required` — обязательные аргументы.
- `risk`: `read` — без подтверждения; `write` и `exec` — с
  подтверждением пользователя.
- `permissions` — что плагину разрешено: `fs:read`, `fs:write`, `net`,
  `exec`. Если поле не указано, набор берётся по `risk`. `fs:write` при
  `risk=read`, а `net`/`exec` при `risk` ниже `exec` — ошибка манифеста.
- `module` — файл `.py` рядом с манифестом.
- `handler` — имя функции в модуле (по умолчанию `handler`).
- Обработчик возвращает `ToolResult(ok, text)`.

После сохранения настроек реестр плагинов перезагружается без
перезапуска приложения.
