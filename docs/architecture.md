# Архитектура Giperion

Проект «Гиперион» состоит из двух направлений и общего слоя.

| Часть | Что это | Зависит от |
|---|---|---|
| `giperion/` | модель ИИ: понимает реплику и отвечает | `shared` |
| `terminal/` | агент: интерфейс, память, навыки, оркестрация | `giperion`, `shared` |
| `shared/` | общий слой: JSON, журнал действий, нормализация текста | — |

Правило направления: **модель не знает про агента**. `terminal` может
импортировать `giperion`, `giperion` — только `shared`. Проверка —
`tests/test_architecture.py`; она падает, если граница нарушена.

## Контракт модели

Единственная дверь в модель — `giperion/api.py`:

```python
from giperion.api import answer

reply = answer("привет")   # ModelReply | None

if reply is None:
    ...  # модель не знает: решает агент
```

`ModelReply` содержит `text`, `source` (`intent` или `neural`) и
`confidence`. Всё остальное — внутреннее устройство модели: правила
`intents.json`, классификатор, seq2seq, пороги уверенности.

Агент вызывает модель на этапах `intent` и `neural` в
`terminal/core/chat_pipeline.py`. Всё, что не является пониманием и
ответом (поиск, калькулятор, время, файлы, смена модели, конференция),
принадлежит агенту.

## Паспорт модели

`data/model_passports.json` — единственный источник числовых фактов о
модели: архитектура, объём данных, качество, диалог, скорость и динамика.
Файл принадлежит модели, агент его только читает:

- окно «Параметры ИИ» строит разделы из паспорта;
- левая панель «ИИ» показывает семь самых динамичных строк;
- `python -m tools.update_passport` пересчитывает измеримые поля
  (параметры, объём данных, accuracy, macro-F1, уверенность).

Ручные поля (уровень, fallback, заметки, скорость) инструмент не трогает:
их измеряют отдельными прогонами.

## Роль Гипериона сегодня

Гиперион — **секретарь**: понимает фразу, относит к намерению, отвечает
коротко, помнит профиль. Это текущая точка роста, а не потолок: модель
развивается независимо от Терминала, и когда она научится отвечать сама
на более широкий круг задач, агент просто перестанет звать внешние модели.

## Два scorecard'а

Сравнивать модель и агента одним числом нельзя: у них разная работа.

### Модель (Гиперион)

- точность намерений (macro-F1) на `data/eval_set.json`;
- fallback rate и time-to-fix непонятых фраз;
- адекватность короткого ответа (0–2) и длина;
- удержание контекста на 2–3 ходах;
- retention после переобучения (падение больше 2 п.п. — регресс);
- стенд запускается без GUI: подали фразы — получили ответы.

### Агент (Терминал)

- task success на составных задачах;
- доля задач, решённых без внешней модели;
- корректность эскалации (внешняя модель была действительно нужна);
- восстановление после ошибок (квота, страна, таймаут);
- стоимость и p95 на задачу;
- **доля разрушительных действий без подтверждения** — главный guardrail,
  когда появятся файлы и управление ПК.

Сравнение с внешним агентом (например, со мной как с агентом) имеет смысл
только на общем наборе задач в домене проекта: короткие русские реплики,
память о пользователе, навыки, контекст. На общих знаниях и коде сравнение
бессмысленно.

## Когда Терминал получит доступ к ПК

Порядок, при котором это не станет опасным:

1. **Белый список операций** вместо произвольного shell.
2. **Подтверждение** для записи, удаления и запуска программ; чтение — по
   настройке.
3. **Журнал действий** (`shared/action_log.py`) с путями и результатом.
4. **Ограничение области**: только папки проекта и явно разрешённые.
5. **Метрики безопасности** в том же scorecard: сколько действий отменено,
   сколько выполнено без подтверждения, сколько упало.

## Git-процесс

- `main` всегда зелёный: `pytest` + `compileall`.
- Работа идёт короткими ветками `arch/*`, слияние в `main` — после тестов.
- Перемещения файлов — только через `git mv`, чтобы работал
  `git log --follow`.
- Один коммит = один шаг: тег `v0.9-baseline`, `v0.9.1-boundary`,
  `v0.10-model-api`, `v0.11-model`, `v0.12-terminal`, `v0.13-split`.

## Как потом развести на два репозитория

Граница готова к этому заранее. Когда появится триггер (свой релизный цикл
модели, внешний потребитель, отдельная команда), модель выносится так:

```bash
git subtree split -P giperion -b giperion-model
```

История `giperion/` сохраняется. После этого `terminal` подключает модель
как пакет или как сервис — код менять не нужно, потому что он уже общается
через `giperion.api`.

Триггеры, при которых это стоит делать: отдельные версии и релизы модели,
несколько потребителей, разные лицензии, разные люди в командах.

## Что осознанно не сделано

- Переименование `model_*` → `provider_*` в `terminal/core` (сейчас слово
  «model» означает провайдера, а не Гипериона). Это отдельный шаг: нужно
  менять и имена функций (`load_models`, `get_model`), и тесты.
- Разделение `tests/` на `tests/model` и `tests/terminal`.
- Вынос `data/` и `models/` внутрь пакетов: данные общие, переезд кода их
  не касается.
