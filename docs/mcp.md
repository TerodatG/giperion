# MCP-серверы в агенте

Агент умеет подключать внешние инструменты по протоколу **MCP**
(Model Context Protocol) — JSON-RPC 2.0 через stdio. Серверы запускаются
как отдельные процессы, их инструменты появляются в реестре рядом со
встроенными.

## Включение

1. Создать `data/agent_mcp.json` (файл вне git):

```json
{
  "servers": [
    {
      "name": "files",
      "command": "npx",
      "args": ["-y", "@modelcontextprotocol/server-filesystem", "."],
      "enabled": true,
      "tools": ["read_file", "list_directory"],
      "domains": []
    }
  ]
}
```

2. В окне агента → «Провайдер…» включить галочку **«Включить
   MCP-серверы»**.
3. Инструменты появятся в следующей задаче как `mcp_<сервер>_<имя>`,
   например `mcp_files_read_file`.

## Поля конфига

- `name` — имя сервера; приводится к `[a-z0-9_]`, попадает в имя
  инструмента.
- `command` / `args` — как запускать процесс (без shell).
- `env` — дополнительные переменные; `${VAR}` подставляется из
  окружения. По умолчанию окружение чистое: только PATH, TEMP,
  SYSTEMROOT и `PYTHONPATH` проекта.
- `enabled` — `false` отключает сервер, не убирая его из файла.
- `tools` — необязательный белый список инструментов сервера. Пустой или
  отсутствующий — разрешены все; иначе остальные даже не показываются
  модели.
- `domains` — необязательный белый список доменов для URL-аргументов
  (`url`, `uri`, `href`, `link`). Поддерживается точное имя и
  `*.example.com` для поддоменов. Пустой — URLs не ограничиваются.
  Запрещённый домен отсекается до обращения к серверу.

## Как это работает

- При первом обращении агент запускает каждый сервер, проходит
  `initialize`, забирает `tools/list` и закрывает процесс; результат
  кешируется до перезапуска настроек.
- Каждый вызов инструмента — новое подключение сервера, запрос
  `tools/call` и закрытие. Таймаут — 20 секунд.
- Ответ собирается из `content` с типом `text` (и `resource.text`);
  `isError: true` превращается в ошибку инструмента.
- `inputSchema` сервера передаётся модели как есть, поэтому работают
  числа, массивы и вложенные объекты. Проверяется только наличие
  обязательных аргументов.

## Безопасность

- Инструмент с `readOnlyHint: true` считается читающим, остальные
  требуют подтверждения (как `write`).
- Сервер — обычный дочерний процесс с правами пользователя. Аудит-хук
  плагинов на него **не** ставится: MCP-серверы бывают на Node, Go и
  чём угодно. Ограничения — только чистое окружение и таймаут.
- Включайте только те серверы, которым доверяете. Файл конфига не
  попадает в git.

## Отладка

- Если инструменты не появились: проверьте, что сервер запускается
  вручную (`command` + `args`), и что он отвечает на `initialize`.
- Ошибки сервера видны в ответе инструмента: «MCP-сервер … не
  запустился», «не ответил за 20 с», «закрыл поток».
- `python -m pytest tests/test_agent_mcp.py` — проверка клиента на
  локальном стенде-сервере.

## Живой пример: mcp-server-fetch

Проверено на настоящем сервере из PyPI (не на стенде):

```powershell
python -m venv data\mcp_venv
data\mcp_venv\Scripts\python.exe -m pip install mcp-server-fetch
```

`data/agent_mcp.json`:

```json
{
  "servers": [
    {
      "name": "web",
      "command": "D:\\Projects\\...\\data\\mcp_venv\\Scripts\\python.exe",
      "args": ["-m", "mcp_server_fetch"],
      "enabled": true
    }
  ]
}
```

После включения галочки «Включить MCP-серверы» в «Провайдере» агент
видит инструмент `mcp_web_fetch` со схемой `url`, `max_length`,
`start_index`, `raw`. Сервер объявляет `readOnlyHint`, поэтому
подтверждение не требуется.

Проверено два уровня:

- `McpClient` напрямую: `initialize`, `tools/list`, `tools/call` —
  страница `https://example.com` прочитана и вернулась текстом;
- живая задача на `qwen3-coder-30b`: модель сама вызвала
  `mcp_web_fetch`, получила страницу и ответила за 7.4 с (6.5k токенов).

Node.js на этой машине нет, поэтому `npx`-серверы
(`@modelcontextprotocol/server-filesystem`) не проверялись; Python-сервер
подтверждает совместимость протокола.

Папка `data/mcp_venv/` не попадает в git.
